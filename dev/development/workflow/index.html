    Development Workflow¶

    Back to Codebase Guide

    Development Setup¶

    Follow Build from source, then install the pre-commit hooks:

    git clone https://github.com/MUNQU/commol.git
cd commol/py-commol
uv sync --extra dev --extra docs
source .venv/bin/activate
maturin develop --release --features test-kind
pre-commit install

    Run maturin develop --release --features test-kind again after every Rust change, before you run pytest. The test-kind feature adds the model kind of the tests (py-commol/src/test_kind.rs); the tests of tests/model_kinds/ need it, and a release build never has it. cargo build --workspace does not link the PyO3 crate outside maturin; use cargo clippy and the per-crate tests instead (see Quick commands).

    Branching Strategy¶

    Commol has one branch, main (trunk-based development): every pull request merges into it, through the merge queue, and a release is a tag on it.

    • main: The integration branch, always tested and releasable. Protected by its ruleset: pull requests only, squash merges through the merge queue, and the required checks. A review is welcome and not required.
    • release/X.Y: Only to fix a version that main has left behind. It is cut from the tag vX.Y.Z, receives fixes copied from main (git cherry-pick), and releases vX.Y.(Z+1). A fix lands on main first.
    • Short branches for one piece of work each, from main, merged within days:
    • feature/*: New features, refactoring, or significant changes (e.g., feature/add-stochastic-model)
    • fix/*: Bug fixes (e.g., fix/calculation-error)
    • docs/*: Documentation-only changes (e.g., docs/update-api-reference)
    • test/*: Test additions or improvements (e.g., test/add-conditional-stratification-tests)
    • chore/*: Maintenance tasks, dependencies (e.g., chore/update-dependencies)

    Planning¶

    Planned work lives in GitHub issues, written from the templates of .github/ISSUE_TEMPLATE/:

    Template Label For
    Proposal (proposal.md) proposal A feature, a refactor or a breaking change: goal, current state, requirements with the tests that check them, decisions, tasks
    Bug or small change (change.md) change A defect or a change that needs no proposal: the behavior, a reproduction and the test that will show it
    Release (release.md) release The checklist of one release, blocked by the issues it ships
    What Where
    The specification of a change The body of its issue
    Decisions and findings during the work Comments of the issue (L<n> (decision|implementation): …), and the Decisions table of the body
    What a change does to other work The bodies and comments of the open issues it affects; work it leaves undone, in an open issue
    Order and dependencies "Blocked by" links between issues; "Why here" in the Delivery of a proposal
    Releases A milestone per release, and its release issue
    Status The commol project: "Board" by status, "By release" by milestone
    Evidence of the delivery The body of the pull request: each requirement and the tests that pass
    What lasts after the delivery The guide, Design decisions and the changelog, as the definition of done requires

    To find the next piece of work, in one call and one line:

    .github/scripts/next.sh        # the next proposal; .github/scripts/next.sh 3 for three

    It lists the open proposals that no open issue blocks and nobody has taken, by the field Order of the project, not by issue number: the dependencies set what must come first, and Order the preference among the proposals that are ready. A new proposal gets an Order between those of its neighbours; the values go in steps of 10 so one fits in without renumbering. To see the whole plan:

    gh issue list --label proposal --state open
gh issue list --milestone 0.5.0

    An issue is ready when every issue that blocks it is closed.

    The project adds a new issue as Todo and moves it to Done when it closes. A pull request that says Closes #N links to its issue and closes it when it merges. In Progress is set when the work starts, by .github/scripts/start.sh (see below), or by hand from the project or a terminal:

    gh project item-list 1 --owner MUNQU                    # the items and their status
item=$(gh project item-list 1 --owner MUNQU --format json \
  --jq '.items[] | select(.content.number == <number>) | .id')
gh project item-edit --project-id PVT_kwDODcfAw84BnXyo --id "$item" \
  --field-id PVTSSF_lADODcfAw84BnXyozhl8usw --single-select-option-id 47fc9ee4  # In Progress

    Lifecycle of a proposal¶

    1. Open the issue from the template: a scoped goal, the current state with paths and symbols, one requirement per behavior (The <component> SHALL …, with WHEN … THEN … scenarios), each scenario with the test that checks it. Add breaking when it breaks the public API, the milestone of its release, its blockers and its Order in the project. A large proposal splits into sub-issues.
    2. Settle its decisions when its implementation starts, not before. A decision that changes what an earlier proposal built, or what a later one relies on, updates those issues too, with a comment in each.
    3. Start it with one command, which takes it, sets it to In Progress and creates its branch from main, linked to the issue, in a sibling worktree:
    .github/scripts/start.sh <number> <type>/<name>   # --here: in this checkout

    It refuses an issue that is closed, blocked by an open issue, or taken by someone else, and --dry-run shows what it would do. Never start by hand: a started issue that is not In Progress and assigned looks free to the next one who runs next.sh. Work one task after the other, the tests of a requirement before its code. Tick the tasks of the body as they land. 4. Update every open issue the change affects, before the pull request merges. To find them, run:

    python .github/scripts/affected.py --closes <number>

    It lists the open issues whose body names a path that the branch changes, in its section Touches or anywhere else, with the items that match. Edit the body of each one whose current state, paths or assumptions the change alters, and add a comment that says what changed. The script finds candidates by path; an issue that relies on a behavior without naming its path needs your own check. Work the change leaves undone goes to an open issue (the one that will do it, or a new one from a template), never only to a comment of the issue that closes: a closed issue is not read again. 5. Open the pull request with Closes #N and the evidence. The merge closes the issue.

    Parallel work¶

    Two proposals can run at the same time when no chain of "blocked by" links joins them and neither changes what the other changes or adds. Each proposal says what it touches (section Touches of the template):

    Kind What it is Conflicts with
    Changes An edit to what exists: a behavior, a signature, a contract other code implements (a required method of SimulationEngine) Any Changes or Adds of the same item
    Adds New code next to what exists: a module, a method of a shared class, a variant, a registry entry Only a Changes of the same item: two Adds to one class merge by keeping both

    An item is a path or path::Symbol; a path that ends in / is a directory. .github/scripts/parallel.py reads the Touches and the links of the open issues, prints the proposals ready now and the ones each can run with, and with --write keeps the line "Parallel with" of each Delivery up to date; run it after a proposal is added or its Touches change. The area: labels filter the same zones (gh issue list --label area:inference -s open).

    To take a proposal while others run:

    1. Start it with .github/scripts/start.sh <number> <type>/<name>: it assigns the issue (an assigned issue is taken), sets it to In Progress and creates its worktree, a sibling of the repository, which needs its own CodeGraph index.
    2. Open the pull request as usual. The merge queue of main tests it on top of the pull requests queued before it, so a conflict in meaning fails there and never reaches main; a conflict in the lines of a shared index (the changelog, AGENTS.md) is solved by keeping both.

    Development Process¶

    1. Starting New Work¶

    # Always start from the latest main
git checkout main
git pull origin main

# Create a feature branch
git checkout -b feature/your-feature-name

    2. Making Changes¶

    # Make your changes to the code

# Run quality checks before committing (with virtual environment activated)
cd py-commol
ruff check . --fix         # Auto-fix Python linting issues
ruff format .              # Format Python code
ty check commol            # Type checking

cd ..
cargo fmt --all                       # Format Rust code
cargo clippy --all-targets --fix      # Fix Rust linting issues

    3. Testing Your Changes¶

    # Run Python tests (with virtual environment activated)
cd py-commol
pytest -v

# Run Rust tests
cd ..
cargo test --workspace

    4. Committing Changes¶

    We follow Conventional Commits for commit messages. The scope is required, and a message is one short phrase with no body; see Commits:

    # Commit format: <type>(<scope>): <description>

git add .
git commit -m "feat(transitions): add rate patterns"
git commit -m "fix(simulation): correct the total of a subgroup"
git commit -m "docs(readme): update installation instructions"
git commit -m "test(models): add tests for stratified models"

    Commit Types:

    • feat: New feature
    • fix: Bug fix
    • docs: Documentation only
    • style: Code style changes (formatting)
    • refactor: Code refactoring
    • test: Adding or updating tests
    • chore: Maintenance tasks, dependencies
    • perf: Performance improvements
    • ci: CI/CD changes
    • build: Build system changes

    Branch vs Commit Type:

    The branch name indicates the primary purpose of the work, while commit types describe individual changes:

    • A feature/refactor-api branch may have refactor, test, and docs commits
    • A test/* branch primarily adds tests but may have fix commits too
    • A docs/* branch is documentation-only, so all commits should use docs type

    5. Pushing and Creating Pull Requests¶

    # Push your branch
git push origin feature/your-feature-name

# Create a Pull Request on GitHub
# - Target 'main'
# - Fill in the PR template; "Closes #N" names the issue it delivers

    6. Code Review and CI¶

    When you create a PR, automated checks run:

    • Code Quality Pipeline: Linting, formatting, type checking for both Python and Rust
    • Build Pipeline: Builds on Ubuntu, Windows, and macOS with Python versions
    • Test Coverage: The Code Quality jobs measure the coverage of Python (pytest --cov) and of Rust (cargo llvm-cov) and upload it to Codecov, which feeds the coverage badges of the README

    PR Requirements:

    • The required checks must pass: Python Code Quality, Rust Code Quality, Build Documentation and Build Passed (the whole test matrix)
    • No merge conflicts with target branch
    • The merge queue: it merges each pull request on top of the ones queued before it, after the required checks pass on that result
    • Code coverage should be >95%

    7. Merging¶

    Once its checks pass, add the pull request to the merge queue ("Merge when ready", or gh pr merge <number> --squash): the queue squash-merges it, the only method main allows, once the required checks pass on top of the pull requests before it. GitHub deletes the branch after the merge (delete_branch_on_merge); delete your local copy with git branch -D <branch> after git fetch --prune.

    A release needs no merge between branches: it is a tag on main (Release Process).

    Dependabot reads its configuration from main

    Changes to .github/dependabot.yaml take effect once they reach main. Updating the file there also triggers a version-update check right away.

    Continuous Integration Pipelines¶

    Workflow Runs on Checks Required check
    Code Quality (code-quality.yaml) Pull requests, the merge queue and on demand Python: Ruff (lint, format, docstrings D1/D417), Ty, Pytest with the documentation checks (pytest -m docs) and its coverage. Rust: rustfmt, Clippy (-D warnings, so missing_docs too), rustdoc without broken links, cargo test with its coverage (cargo llvm-cov). Both upload their coverage to Codecov (flags python and rust) with the OIDC token of the run, so no secret is needed; .github/codecov.yml makes its checks informational. Python Code Quality, Rust Code Quality
    Build (build.yaml) Pull requests, the merge queue, every Monday on main and on demand Tests, except the documentation checks and the coverage studies. A pull request runs one job, Ubuntu with Python 3.12, for a fast answer; the merge queue, the weekly and the manual runs test Ubuntu, Windows and macOS with Python 3.12, 3.13 and 3.14. A failure that only one operating system shows appears in the queue, which then removes the pull request. A change of only documentation or planning files (docs/, Markdown at the root, mkdocs.yaml, .github/ISSUE_TEMPLATE/, .github/scripts/) skips the tests. The wheels of every architecture are built by the release (release.yaml). Build Passed
    Documentation (docs.yaml) Pull requests, the merge queue, pushes to main and release tags mkdocs build --strict: no broken internal link or anchor. Deploys the site with mike: a release tag as latest, a push to main as dev. Build Documentation
    Coverage Studies (coverage.yaml) Every Monday; on demand pytest -m coverage_study: the intervals of each uncertainty method cover the truth at their level (Design decisions). None: each study runs many fits
    Links (links.yaml) Pull requests that change docs/, README.md or AGENTS.md; every Monday; on demand External links, with lychee. None: a site that is down for a while must not block a pull request
    Merge queue (merge_group in Code Quality, Build and Documentation) A pull request queued for main The same required checks, on the pull request merged on top of the ones queued before it, at most 2 groups at a time and up to 5 pull requests per group. The tree that reaches main is the tree the queue tested, so a push to main runs no tests again. The same
    Release (release.yaml) A published GitHub release Builds wheels and the sdist, and publishes them to PyPI. See Release Process. —

    Local Development Tips¶

    Quick Commands¶

    # Python, from py-commol/ with the virtual environment active
ruff check . && ruff format --check . && ty check commol
vulture commol .vulture_allowlist.py --min-confidence 80 && pytest

# Rust, from the repository root
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test -p commol-core -p commol-model -p commol-difference -p commol-differential -p commol-calibration -p commol-inference -p commol-random -p commol-stochastic -p commol
cargo test -p commol --features test-kind   # the engine of the test model kind

# Coverage studies (slow), from py-commol/
pytest -m coverage_study

# Test coverage, as CI measures it (Rust needs `cargo install cargo-llvm-cov` and
# `rustup component add llvm-tools-preview`)
pytest --cov=commol                           # from py-commol/
cargo llvm-cov --all-features --workspace     # from the repository root

# Documentation, from the repository root
mkdocs build --strict

    Pre-commit Hooks¶

    Install pre-commit hooks to automatically check code before committing:

    cd py-commol
pre-commit install

    On every commit, the hooks in .pre-commit-config.yaml run:

    Hook Checks
    cargo-fmt Rust formatting
    cargo-clippy Rust lints with -D warnings, including missing_docs
    ty-check Python types of commol
    vulture Dead Python code
    ruff-check Python lints, including docstrings (D1, D417)
    ruff-format Python formatting
    uv-lock uv.lock matches pyproject.toml

    The Python hooks run their tool with uv run from py-commol/, so they use the versions of uv.lock, the same as CI. Dependabot updates uv.lock, not the rev of a pre-commit repository, so a hook pinned there would drift from CI.

    The Rust toolchain¶

    rust-toolchain.toml pins one Rust version, with clippy and rustfmt. rustup installs and uses it in the repository, so your builds, the pre-commit hooks and CI (rustup toolchain install, and maturin-action, which reads the file) run the same compiler and the same lints. A floating stable would let a lint of a newer clippy pass on your machine and fail in CI.

    Once a month, Dependabot (.github/dependabot.yaml, ecosystem rust-toolchain) checks for a newer stable release, and opens a pull request to main that changes channel. Its CI runs the new clippy, so the new lints fail there, not in a feature branch. To move to a newer Rust by hand, or to fix the lints of that pull request:

    1. Change channel in rust-toolchain.toml.
    2. Run cargo clippy --workspace --all-targets --all-features -- -D warnings, the Rust tests and cargo doc (see Quick Commands), and fix what the new lints find.
    3. Rebuild the extension and run pytest.

    Debugging Rust from Python¶

    # Build with debug symbols (with virtual environment activated)
cd py-commol
maturin develop

# Run Python
python -m your_test_script.py

    Building Documentation¶

    The project uses MkDocs Material for documentation with multi-version support via Mike:

    # Install documentation dependencies (with virtual environment activated)
cd py-commol
pip install -e ".[docs]"

# Serve documentation locally
mkdocs serve

# Build documentation
mkdocs build

    Visit http://127.0.0.1:8000 to view the documentation locally.

    Documentation Versioning¶

    Commol maintains two documentation versions:

    • latest: Documentation of the last release, built from its tag
    • dev: Development documentation, built from main

    Automatic Deployment¶

    Documentation is deployed automatically:

    • A release tag vX.Y.Z: deploys the latest version
    • A push to main: deploys the dev version
    • Pull requests: Build and validate documentation without deploying

    Users can switch between versions using the version selector in the documentation site.

    Manual Deployment (if needed)¶

    If you need to manually deploy documentation:

    # Deploy latest version (from a checkout of the release tag) - with venv activated
cd py-commol
mike deploy --push --update-aliases latest
mike set-default --push latest

# Deploy dev version (from main)
cd py-commol
mike deploy --push dev

# List all deployed versions
mike list

# Delete a version
mike delete <version-name> --push

    Version Management Tips¶

    • The version selector appears in the top-right of the documentation site
    • Each version is completely isolated with its own search index
    • Old versions remain accessible even after new deployments
    • Use mike list to see all deployed versions and aliases
