    Design Decisions¶

    Back to Codebase Guide

    The rules on this page are not obvious from the code, and breaking one gives results that are wrong but look correct. Each rule names where it lives and the test that guards it. Read the ones of your area before you change it.

    Area Decisions
    Model kinds One interface for every kind, a model by composition, neutral terms
    Model structure Compartments, what they hold, stratification order, outputs, variable names
    Transitions and rates Rate semantics, stratified rates, formula parameters, JIT cache
    Initial conditions Subgroup totals, calibrated values
    Time Physical units, step unit, time inside a step, impulses, windowed observations
    Engines One set of flows, seeds, whole units, solver
    Calibration Weights, Nelder-Mead bounds, simulations
    Results Confidence intervals, descriptions, reports, model files
    Security Expressions

    Model kinds¶

    One interface for every model kind¶

    The layers that do not depend on how a model is built (Simulation, Calibrator, ProbabilisticCalibrator, the reports and SimulationPlotter) use only Model and the methods of ModelStructure (py-commol/commol/context/structure.py), and in Rust only the SimulationEngine trait (crates/commol-core/src/simulation_engine.rs). What only an aggregate model has (compartments, initial fractions) is behind them: Aggregate (context/aggregate.py), and in Rust CompartmentalEngine and InitialConditionPlan (crates/commol-model/). A new kind, such as an agent network, is a new ModelStructure subclass with its engines in the list; nothing that exists changes.

    Part Rule Why, against the alternative
    ModelStructure An abstract base class (Pydantic's metaclass derives from ABCMeta). A missing method fails when the object is made and names it; optional methods have a default. A typing.Protocol shows a missing method only under ty, or mid-run as an AttributeError, and gives no defaults.
    Engine kinds An engine names a method, not a kind: each entry of EngineType names the kinds it runs (EngineType::kinds). Model asks the list (check_kind) when it is made, and Engine::build asks it again and picks the implementation by the pair of the engine and the kind; the error names the engine, both kinds and the engines of the kind of the model (EngineType::engines_of). Without the check, a model of one kind reaches the engine of another and fails deep in its compilation. One engine per kind would multiply the names: a stochastic engine runs every structure that implements it.
    Values calibration sets parameter and factor are generic. Each kind declares the types of value of its own it accepts (ModelKind::value_types, which ModelStructure.calibration_value_types asks); the aggregate kind accepts initial_condition. The engine resolves and writes them (SimulationEngine::plan_values, apply_values). The calibration crate would know compartments, and a new kind could not calibrate values of its own without editing it.
    Report sections ModelStructure.report_sections adds the sections of a kind to applied_parameters_report (default: none); the aggregate kind adds initial_conditions. A check of the kind in reporting.py brings back a branch per kind.
    Expressions in constraints The engine names the values of an output row: output_names, state_outputs (their sum is total) and output_sums (a bin total, for an engine of the aggregate kind). The calibration would rebuild bin totals from compartment labels.

    The test kind (tests/support/kinds.py, engine TestEngine in py-commol/src/test_kind.rs) is written only against the interface. The extension has it only when it is built with the cargo feature test-kind, as the tests and CI build it; a release build does not.

    Guards: tests/model_kinds/ (a test model through a simulation, a calibration, a report and a plot; the kind check both ways; a process the test kind cannot run), crates/commol-calibration/tests/test_model_values.rs (the calibration with an engine that is not of the aggregate kind: values through plan_values and apply_values, constraints through output_sums and state_outputs), py-commol/src/engine.rs::an_engine_rejects_a_model_of_another_kind, crates/commol-core/src/types/engine.rs::an_engine_rejects_a_model_of_another_kind.

    A model is a header, a process, a structure and an engine¶

    Model (Python context/model.py, Rust crates/commol-core/src/types/model.rs) is one class for every kind: name, description, version, step_unit, parameters, engine ({type, settings}), process and structure. The process (Process: bins, accumulators, stratifications, transitions) is what changes and how, written once. The structure is what changes between kinds of model: Aggregate lays the process out as amounts per compartment; Network and Agents come with their proposals (#144, #145). It is tagged in JSON by kind. In Python Model is generic in its structure class: ModelBuilder.build(structure, engine) returns a Model of the class of structure (a TypeVar, never a value), so model.structure.total type-checks, and Model.from_json reads the class from the kind and variant of the file. The engine is part of the model because it sets what a rate means.

    The interface of a kind stays on the structure and reads the process from the model (outputs_by_source(model), series_label(model, id)); the methods of Aggregate that need the bins take the process (initial_state(process)).

    Alternative Why not
    Inheritance: an abstract Model with a CompartmentalModel Direct access (model.bins), but two parallel hierarchies, of models and of builders, and the header repeated per kind. With composition, Simulation and Calibrator take one type.
    A builder per kind (NetworkModelBuilder, …) The user writes the same transitions again for each kind.
    One structure per kind that holds its own transitions The same duplication, inside the model files.
    A setting of the engine that picks the structure A graph or a set of agents is data of the model, not a setting; the file would not reproduce a run.
    A structure that holds a reference to its process Two copies to keep equal: a model copied or changed would carry a stale process.

    A structure may have variants: a subclass that keeps the kind, the fields and the engines of its structure, narrows the constructor and may add checks (MarkovChain(Aggregate), Network(Agents) in later proposals, #142 and #144). The JSON holds the kind and the variant; the Python registry (ModelStructure._kinds) is keyed by (kind, variant), so a model loads back as the class it was saved with. Rust reads the variant only to run its checks (AggregateVariant::check), so the engines do not change. A subclass with no tag would load back as its base class and compare unequal; a kind per narrower form would split the structures again.

    The fractions of Aggregate are mappings by id (bin_fractions={"A": 0.99}), in Python and in the file, and Rust keeps their order (IndexMap). A list of {"bin", "fraction"} records needs a second shape for the constructor, and Pydantic calls a custom __init__ when it validates a file too.

    Guards: crates/commol-core/src/types/model.rs (tests), tests/building/test_save_and_load.py, tests/model_kinds/test_interface.py::TestStructureInterface, tests/model_kinds/test_interface.py::TestVariants, tests/building/test_engine.py::TestBuild.

    Neutral terms carry a process across structures¶

    A rate may read neighbors_<bin>, the amount of a bin among the neighbors of a unit, and neighbors, their total. They carry a process from one structure to another: a rate that reads them and no compartment is proportional, a rate per unit of its source, which a network or an agent model reads per node or per agent. Under Aggregate the structure says who the neighbors are, with no default:

    Aggregate.neighbors neighbors_<bin> from a compartment of category g neighbors
    Complete() The bin total total
    Groups(stratification, weights) Σ_g' w[g][g'] × (amount of the bin in g') Σ_g' w[g][g'] × (amount of every bin in g')

    plan_transition_flows (crates/commol-model/src/flows.rs) decides whether a rate is absolute before resolve_neighbors writes the terms as the sums they are, found by label (CompartmentLayout::with_category), so k1 * neighbors_B / neighbors from A is the proportional flow k1 × A × B / total under Complete(). check_model (crates/commol-model/src/builder.rs) reserves the names, rejects a neighbors_<id> that names no bin and a formula parameter that reads them, and asks for neighbors when a rate reads them; Neighbors::check checks the groups and their weights.

    Every term is neutral: no "population", "size" or "contact", which assume individuals and a field. A default of Complete() would choose a modelling assumption for the user.

    Guards: tests/transitions/test_neighbors.py, crates/commol-model/src/flows.rs (tests complete_neighbors_…, group_neighbors_…, a_rate_that_reads_the_neighbors_…), crates/commol-model/src/builder.rs (tests a_name_of_the_neighbors_…, a_rate_reads_the_neighbors_of_a_bin_only_when_the_structure_has_them).

    Model structure¶

    Compartments are labels with a name¶

    A compartment is a bin plus one category for each stratification that applies to it, in declaration order. Its name, {bin}_{category}_{category}…, is for display only. Its identity is its label: OutputLabels in crates/commol-model/src/labels.rs and CompartmentLayout in crates/commol-model/src/layout.rs.

    Rule: never parse a compartment name or match it by prefix. Bin A and bin A_x both produce names that start with A_, and a conditional stratification gives some compartments fewer suffixes than others. Use CompartmentLayout::find or of_bin in Rust, and the labels that the engine queries return in Python.

    State, amount, total and subgroup total¶

    The library names what the compartments hold without assuming individuals:

    Term Meaning Where
    State The vector of the amount of every compartment CompartmentalEngine::state, Engine.state
    Amount The value of one compartment InitialCompartment.amount
    Total The sum of every compartment, accumulators excluded; the initial fractions are taken of it InitialConditions.total, the rate variable total (SPECIAL_VAR_TOTAL)
    Subgroup total The sum of the compartments with some categories subgroup_total, the rate variables total_<cat>… (SUBGROUP_TOTAL_PREFIX)

    The total is a real number, finite and greater than 0, so a model of a count, a mass or a concentration can be stated. 0 is rejected: every fraction of it is zero, and the report divides by it (initial_state in crates/commol-model/src/builder.rs, InitialConditions.validate_total).

    Rule: use these four terms in code, docs and tests. AxisPattern takes a value, so "amount" means only the value of a compartment.

    Why, against the alternatives:

    Alternative Why not
    "population", "head count", N They assume individuals and an epidemiological convention (N = S + I + R). A reserved N takes a letter that other fields use for a bin, such as a nutrient.
    "mass" A unit, not a quantity of any unit.
    "stock" An economic term, new to the code.
    "content" Ambiguous in software.
    "size" Reads as a count, and clashes with the NSGA-II population_size.
    A function total(g1, t1) No reserved names, but the expression language has no text arguments (jit/ast.rs), so the parser, the JIT and the security check would change.

    Guards: builder.rs tests a_real_total_starts_with_amounts_that_sum_to_it and a_total_that_is_not_finite_and_positive_is_a_build_error; tests/building/test_reserved_names.py::test_a_bin_named_n_builds_and_runs; tests/initial_conditions/test_bin_fractions.py::TestTotal.

    Stratification order is part of the model¶

    expand in crates/commol-model/src/builder.rs applies the stratifications in declaration order. A stratification with conditions only expands the compartments whose earlier categories satisfy all of them, so the result can be a non-uniform product. A condition may only reference a stratification declared before it (ModelBuilder.add_stratification checks this).

    Rule: changing the order of add_stratification calls changes which compartments exist and what they are named.

    Outputs are resolved by label¶

    Aggregate.outputs_by_source(model) maps each bin or accumulator id to its output names in engine order. It uses the engine expansion (expanded_outputs), so Simulation.outputs_for, group_outputs and total_series group outputs by label, not by name.

    Guards: tests/simulation/test_outputs.py::TestOutputsBySource::test_expansion_matches_the_engine_output_names (order) and TestSourceIdSharingAPrefix (a bin and an accumulator that share a prefix).

    The engine owns the variable names¶

    The engine sets one variable per expanded compartment and per subgroup total (total_<categories>, bin totals and partial bin totals). check_model in crates/commol-model/src/builder.rs rejects a parameter id that is one of those names, a parameter, bin or accumulator id that is an engine variable (ENGINE_VARIABLES: total, step, t, pi, e) or a name of the neighbors (neighbors, neighbors_…), a bin whose compartments or bin totals read as a total_<categories> name (two sums would share one slot), and a total_… variable in a rate or a formula parameter that names no subgroup total. Aggregate.check_model calls it at build, and CompiledModel::try_from_model calls it again. subgroup_total_names lists the names; Python reads them through the binding commol_rs.model.subgroup_total_names (engine_state.subgroup_total_names) to check rates and give units.

    Rule: never list these names in Python. Ask the engine.

    Guards: builder.rs tests parameter_id_cannot_be_a_compartment_or_a_subgroup_total, subgroup_total_out_of_declaration_order_is_a_build_error and subgroup_total_names_follow_the_declaration_order, an_engine_variable_is_not_a_parameter_bin_or_accumulator_id and a_bin_name_that_reads_as_a_subgroup_total_is_rejected; tests/building/test_reserved_names.py; tests/rates/test_expressions.py::TestSubgroupTotals::test_every_name_the_engine_provides_is_accepted_in_a_rate.

    Transitions and rates¶

    Absolute and proportional rates¶

    The flow planner (plan_transition_flows in crates/commol-model/src/flows.rs) decides for each flow whether the rate is absolute or proportional:

    Case Rate is Flow per step
    A stratified rate sets absolute As set —
    The rate references a compartment, a bin total, total or a total_… variable Absolute rate
    The transition has no source Absolute rate
    Otherwise Proportional rate × source

    A transition with several sources and a proportional rate is rejected, because it has no single source to multiply. Model.describe shows the planned flows, so a proportional rate prints as k1 * A.

    The name says what the flow is: proportional to its source. The name "per-capita" counts heads, which assumes the source holds individuals; a source can hold a mass or a concentration. "Relative" would clash with the relative tolerance rtol of the ODE solver, and "per-unit" with units of measure.

    Guard: tests/transitions/test_flows.py.

    The most specific stratified rate wins¶

    For each compartment, the stratified rate whose conditions match it with the largest number of conditions wins (helpers.rs). On a tie, the first one in the list wins. If none matches, the transition's default rate applies. Building a model fails if a stratified rate matches no compartment that the transition starts from.

    Formula parameters are evaluated every step, in order¶

    Parameters with a formula are evaluated again at each step, in the order they were declared (simulation.rs). A formula can use the value of an earlier formula from the same step. Declare parameters in dependency order.

    Compiled expressions are cached globally¶

    JIT_CACHE in crates/commol-core/src/math_expression/mod.rs maps each preprocessed formula to one compiled function for the life of the process. The same formula always runs the same machine code, so results are reproducible.

    Rule: do not invalidate or bypass the cache.

    Initial conditions¶

    Subgroup totals compose down the condition chain¶

    The fractions of a conditional stratification are relative to the subgroup that its conditions select, not to the total. Subgroup totals therefore multiply along the chain: total × fraction(group1) × fraction(cat1). Aggregate.subgroup_total and Aggregate.get_conditioning_categories own this (context/aggregate.py); with per-compartment overrides, subgroup_total sums the state the engine builds.

    Guard: tests/simulation/test_outputs.py::TestSubgroupTotal compares the result with the state the engine starts from.

    Calibrated initial conditions are applied in layers¶

    InitialConditionPlan in crates/commol-model/src/initial_conditions.rs applies calibrated values in a fixed order: bins, category splits, exact compartments, and then the remainder named by CalibrationProblem.initial_condition_remainder. Both engines of the aggregate kind resolve and write initial conditions through it (SimulationEngine::plan_values and apply_values), and the calibration writes every value through the engine (ValueWriter in crates/commol-calibration/src/values.rs), so the objective, the predictions and the write-back (configured_engine, then the binding calibrated_initial_state) agree by construction. Aggregate.with_calibrated_values (context/_model/calibration_write_back.py) writes the values back as fractions, and pins as per-compartment overrides every compartment that the fractions cannot reproduce.

    Guards: tests/calibration/test_write_back.py::TestApplyCalibrationParameters::test_applied_model_reproduces_the_loss_the_optimizer_scored; crates/commol-model/tests/initial_conditions.rs (the layers, the remainder and the targets of an id). See also Per-compartment initial conditions.

    Time¶

    Physical units are not in the model¶

    A Model records no step length: rates are per step and positions and periods are step counts. The axis of a model is its independent variable, whatever quantity it is (time is one case), so the engines never ask which dimension it has. Model.step_unit is optional; only the unit check and AxisUnits read it. AxisUnits (context/axis_units.py) converts a value in any unit of the step dimension to steps on pint, and Model.axis_units() builds it from step_unit (or step) and the engine of the model. steps returns a float and snaps a result within 1e-9 of an integer to it; whether a position must be whole is the engine's check, not the converter's. The window grid is in api/windows.py.

    The rate conversions (rate_from_mean_span, rate_from_probability) ask the engine: RateMeaning::rate_from_mean_span and rate_from_probability (crates/commol-core/src/types/engine.rs) hold the formula of each meaning, so a new engine picks a meaning and Python does not change. The per-step rate from a mean span is 1 - e^(-1/n): it keeps the survival of the continuous process at every step, and its mean residence is 1/rate, not n (10.508 steps for n = 10). r = 1/n keeps the mean and loses the survival.

    Rule: no formula of a rate per engine in Python; ask the engine.

    Guards: tests/simulation/test_axis_units.py, crates/commol-core/src/types/engine.rs (tests a_rate_from_…), tests/simulation/test_windows.py::TestWindowGrid.

    One step unit in the unit check¶

    The engine converts no value between units. So UnitChecker._step_unit (context/_model/units.py) uses one step unit: the declared Model.step_unit, of any single dimension (check_step_unit), or else step, the default increment of any axis (dimension [step]). The check never infers the step unit from the parameters: a parameter in 1/meter may be a density, not a rate along the axis, and inferring only from units of time gives time a privilege that no other axis has. Without step_unit, a failed check says to declare it. The check reads the flows the engine plans (transition_flows, in UnitChecker._collect_unit_errors), so a proportional rate is checked as its flow, rate × source, and never by a rule of its own in Python. check_equation_units requires every flow to be equal to <bin unit>/<step unit>, and every impulse to <bin unit>, not only convertible to it (utils/equations.py, same_unit).

    A unit means what pint defines; there is no list of aliases. A name that pint does not define becomes the one unit of its own dimension (define_units). In the check, t (a position) has the step unit and step (a count) is dimensionless. A number written in a rate and added to, subtracted from or compared with a quantity is read in its unit, as the engine reads it (parse_equation_unit); a computed number stays dimensionless.

    Rule: never accept a convertible unit as equal. 1/week and 1/day in one model would read a weekly rate as a daily one.

    Guards: tests/units/test_model_units.py::TestConsistentModels (test_a_proportional_rate_is_checked_as_its_flow), tests/units/test_model_units.py::TestStepUnit, tests/units/test_model_units.py::TestAxisUnit, tests/units/test_model_units.py::TestPositionOnTheAxis.

    Time inside a step¶

    A differential model integrates in continuous time, but on [n, n + 1) its rates see step = n: t is continuous, step is the floor of t. A rate that reads step or a "pulse" series (and so AxisPattern.pulse, pulses, periodic) is therefore constant on its unit interval. When the right-hand side reads one of them (CompiledModel::depends_on_step), the engine ends a piece of integration at every integer, so each jump of the rate is the start of a piece (breakpoints in crates/commol-differential/src/solve.rs).

    A "step_function" or "linear" series reads t (SeriesParameter::evaluate), so it holds or interpolates from any position. The engine ends a piece at each of its points (CompiledModel::series_points), where the series jumps or bends. A difference engine reads t = step, so it gives the same values as before, and it rejects a point between integers.

    A rate can also jump where t reaches a value it compares t with (t >= t_on, and so AxisPattern.interval and linear_ramp). The compiler collects those values when they read only numbers, pi, e and parameters that do not change during a run (time_thresholds in crates/commol-model/src/builder.rs), and the engine evaluates them with the current parameters and ends a piece there. Without that, an adaptive solver whose rate is 0 before a short window grows its step and steps over the window. A comparison with the state is a state event, which the engine does not detect.

    On a piece [start, end) the right-hand side sees t no larger than the float just below end (RightHandSide::last_t). A Runge–Kutta step evaluates the right-hand side at the end of its interval; without the limit, a value that jumps at end would already act on the last step of the piece.

    Whether an expression reads step comes from reads_variable, not from get_variables: get_variables leaves out the special variables, because it lists the variables a model must define.

    Consequence: a proportional pulse p moves p of its source in a difference model and 1 − e^(−p) in a differential model. An impulse moves p in both. The alternative, step = t, makes a pulse step == n true on a set of zero length, so it would never act.

    Guards: tests/simulation/test_differential.py::TestTimeInsideAStep, crates/commol-differential/src/tests.rs::a_pulse_rate_is_a_constant_rate_on_its_unit_interval, a_rate_reads_the_step_of_its_unit_interval, a_rate_that_switches_on_t_acts_only_on_its_window, a_linear_series_matches_the_integral_of_its_interpolant, a_step_function_series_holds_from_a_position_between_steps, crates/commol-model/src/builder.rs::a_comparison_of_t_with_a_fixed_value_is_a_threshold, tests/axis_patterns/test_pattern_runs.py::TestDifferentialIntegration.

    Impulses come before the flows of their step¶

    At step n the state jumps first, then the flows of the step run from the new state, in both engines (CompiledModel::apply_impulses). Every jump of one step is computed from the state before any of them. The output at n shows the state after the jump. With the other order, the differential output at n would show the state before the jump and the difference output the state after it, so the two engines would disagree at the output steps. A difference model needs integer impulse steps; a differential model stops its integration at each impulse step and restarts from the new state, so diffsol needs no event.

    Guards: tests/transitions/test_impulses.py::TestJump, crates/commol-differential/src/tests.rs::an_impulse_moves_its_fraction_at_once_in_both_engines.

    Windowed observations¶

    An observation at at with window = W is compared with output(at) - output(at - W), anchored at its own position. The Rust loss and windowed_totals (api/windows.py) must give the same number, and so must the ensemble statistics (StatisticsCalculator._member_window_value). Window w covers (w · W, (w + 1) · W]; window_index places a position with max(ceil(at / W) − 1, 0), and observed_report calls it.

    Guards: tests/simulation/test_windows.py::TestAgreementWithTheCalibrationLoss (the loss at the generating parameters is zero), tests/reporting/test_simulation_report.py::test_observed_report_places_each_observation_by_window_index and tests/probabilistic/test_calibrator.py::test_windowed_bands_are_taken_at_the_observation_positions.

    The engine owns positions¶

    A position on the axis is an f64 in every engine call and a float in every public Python name (at); a length is window or period; a count of steps keeps num_steps. The SimulationEngine trait (crates/commol-core/src/simulation_engine.rs) runs only at positions (run_at_positions_into_buffer); run(n) runs on the grid the engine builds, grid(n), and returns it. Each engine says which positions its model type accepts (check_position): a difference engine non-negative integers, a differential engine any finite, non-negative position. The engine checks every position where it receives it, and its message names the object that holds a rejected one: the observation or constraint (check_positions in crates/commol-calibration/src/calibration_problem.rs), the impulse transition or series parameter (DifferenceEquations::from_compiled).

    Rule: Python passes positions on and shows the engine's message. It never checks whether a model type accepts a position.

    Guards: crates/commol-calibration/tests/test_positions.rs, crates/commol-difference/src/simulation.rs::integer_positions_are_accepted_and_others_rejected, crates/commol-differential/src/tests.rs::a_difference_engine_names_a_series_point_between_steps, tests/calibration/test_observations.py::TestPositionsAndTypology.

    Results carry their positions¶

    Simulation.run and run_at return SimulationResults (api/results.py): a dict from output name to values, with the positions in positions and the rows in rows(). A dict keeps results["A"], json.dumps and pandas.DataFrame(results) working; a reserved key could clash with an output name. Windows, reports, plots and ensemble statistics read a value at a position (index_at, which matches within a relative 1e-9), never at a list index, so a model type that reports between integers fits them. The ensemble trajectories hold StatisticsCalculator.positions: the unit grid and every observation position and window start.

    Guards: tests/simulation/test_runs.py::TestResults, tests/reporting/test_simulation_report.py::TestNonIntegerPositions, tests/plotting/test_plotter.py::TestDifferentialModel, tests/probabilistic/test_differential.py.

    Engines¶

    One list of engines¶

    EngineType (crates/commol-core/src/types/engine.rs) is the one list of model types. An entry is an engine, named by its type (DifferenceEquations, DifferentialEquations, StochasticEvents, StochasticSteps): a method, not a kind. It names the model kinds it runs (EngineType::kinds; today all four run aggregate). Each entry validates its settings and says the form of its dynamics (DynamicsForm: the schedule a description shows and the left-hand side of its equations) and the meaning of a rate (per_step or continuous). Engine::build (py-commol/src/engine.rs) builds the engine of an entry. A model holds its engine and the settings of that engine, Model.engine = {type, settings}, because the engine sets what a rate means, so a saved model reproduces its runs.

    Python asks the list (commol_rs.engine.EngineType): it builds the engine, writes the left-hand side of an equation and the schedule of a description, and checks settings through it, and never branches on an engine name. It keeps the names of the engines only as the Literal EngineName (context/engine.py), for static typing and completion of ModelBuilder.build; a test checks that it equals the entries of the list (test_the_python_names_equal_the_engines_of_the_list). ModelEngine.type is a str that the list checks, so a model can name an engine of any kind; its settings are read with the class of that engine (ModelEngine.settings_of_the_engine), so a model loads back with the class it was saved with. Generating the Literal from Rust would need a code-generation step for four names; the test catches the same drift. An entry names the kinds it runs, so another kind (for example an agent network) adds kinds to an entry or new entries, not a second meaning of the type; see One interface for every model kind.

    The builder takes the structure, the engine and its settings where it chooses them, build(structure, engine, settings=None), so one builder builds a model for each structure and engine with its own settings. Settings of one engine given to another raise an error from the engine that names both.

    Guards: crates/commol-core/src/types/engine.rs (tests), py-commol/src/engine.rs::every_entry_builds_its_engine_and_runs, tests/building/test_engine.py.

    Every engine reads one set of flows¶

    A compiled model is a set of flows (crates/commol-model/src/system.rs): CompiledModel::flow_rates gives the value of each flow, its rate times its source for a proportional rate (transition_rates gives the rate alone), and CompiledModel::flow_changes gives the change of the state of one event of each flow: −1 for each source piece, +1 for each target piece and each accumulator. Every engine reads them, and none has flow logic of its own:

    Engine Reads
    DifferenceEquations derivatives, Σ changes × flow, added once per step
    DifferentialEquations derivatives, integrated
    StochasticEvents flow_rates as propensities, and one event of flow_changes at a time
    StochasticSteps transition_rates as per-step probabilities, and the drawn number of events of each flow

    derivatives is flow_changesᵀ · flow_rates, computed piece by piece in the order of the old right-hand side, so the deterministic runs did not change by a bit. The deterministic engines are the mean-field limits of the stochastic ones, which gives the main test oracle. The positions where a rate can jump come from the same model (CompiledModel::breakpoints), so the differential and the continuous-time stochastic engines stop at the same positions.

    Guards: crates/commol-model/tests/flows.rs, crates/commol-difference/src/simulation.rs::one_step_adds_the_derivatives_exactly, crates/commol-stochastic/tests/oracles.rs (the_mean_of_many_runs_is_the_solution_of_the_ode, the_mean_of_many_chain_binomial_runs_is_the_difference_engine).

    A difference step never leaves an amount below zero¶

    DifferenceEquations checks every compartment after the impulses of a step and after its flows (DifferenceEquations::step, settle in crates/commol-difference/src/simulation.rs). An amount below −10⁻¹² × total, the total at the start of the step, stops the run with SimulationError::Infeasible (crates/commol-core/src/simulation_engine.rs). The message names the compartment, the step, its amount before the step and the flows that drain it (CompiledModel::outflows, impulse_outflows). The check reads the state and the right-hand side once, with no allocation, and the state stays as it was before the step. Accumulators are not checked: a net flow may count negative.

    An error, for every cause, and not:

    Alternative Why not
    A check only of proportional rates that sum above 1 None of the seven negative runs the test suite had broke that rule: they came from absolute rates on a bin total and from rates that turn negative.
    A warning A negative amount is never a correct state, and a warning inside a loop of calibrations is lost.
    Clamp the amount to zero The total is no longer kept, and the flows are no longer those of the model, without notice.
    Scale the outflows down to what the compartment holds A different model, chosen by the library; modelling choices belong to the user.

    Calibration tells such a run from a failure by its type, not by its message. SimulationEngine returns SimulationError: Infeasible { position, message } for a state outside the values the model allows, and Failed(String) for every other error. CalibrationProblem::cost gives an infeasible run the base penalty, as it does for values that are not finite, and records nothing in the history; a failed run still stops the calibration, so a rate that cannot be evaluated does not hide behind a poor fit. An optimizer that explores the bounds of a rate would otherwise stop on the first infeasible point, though the fit lies elsewhere. The predictions of an ensemble return the type as CalibrationError::Infeasible. Python receives InfeasibleStateError, a ValueError (simulation_error in py-commol/src/engine.rs); a failed run stays a RuntimeError.

    The differential engine is not checked: a solver may step below zero by its tolerance, and a model whose exact solution goes negative is a modelling choice there.

    Guards: crates/commol-difference/src/simulation.rs (flows_that_move_more_than_a_compartment_holds_stop_the_first_step, a_rate_that_turns_negative_stops_the_step_where_an_amount_drops_below_zero, proportional_rates_that_sum_to_one_empty_a_compartment, an_impulse_that_moves_more_than_its_source_holds_stops_its_step, an_accumulator_may_count_a_negative_net_flow), crates/commol-calibration/tests/test_infeasible_runs.rs.

    Stochastic engines and seeds¶

    A stochastic engine draws every random number from one generator seeded by SimulationEngine::set_seed (crates/commol-core/src/simulation_engine.rs); reset restores it, so a run is reproducible from its seed. The default set_seed does nothing, so the deterministic engines did not change. EngineType::is_stochastic says which engines draw: StochasticEvents and StochasticSteps (crates/commol-stochastic/). A run does not depend on the positions it reports at: StochasticEvents measures each wait from the last change of the state, never from a reported position, and draws the flow of an event only when the event happens.

    Part Rule
    Generator Xoshiro256PlusPlus of rand_xoshiro, seeded by four SplitMix64 numbers of the seed (Generator in crates/commol-random/). Its sequence is the same on every platform and version.
    Samplers Exponential, Poisson, binomial and multinomial written in commol-random (sample.rs), not taken from rand_distr, whose values may change in a minor version. A test holds the first values of each for a fixed seed.
    Replicates Replicate i of seed s takes replicate_seed(s, i), the SplitMix64 of s + i. run_replicates runs them in parallel (rayon); a deterministic engine has no replicates.
    Calibration Common random numbers: the same replicate seeds at every evaluation, so the loss is a deterministic function of the parameters (CalibrationProblem::with_replicates). The user chooses the summary (ReplicateSummary); LossConfig computes it.

    Reproducibility has three levels: the same machine and commol version give the same run; another platform gives the same random numbers, but the rate functions come from the system's libm through the JIT (math_expression/jit/libm.rs), which can differ in the last bit, so a run there is equal in distribution and rarely differs draw by draw; another commol version may change a run, and the changelog says so.

    Alternative Why not
    A random source passed to every call The trait grows an argument that the deterministic engines ignore.
    The seed in the model file A model is a description; the seed belongs to a run, as CalibrationProblem.seed does.
    StdRng or SmallRng StdRng is slower and its security is not needed; SmallRng is documented as not portable.
    A pure-Rust libm in the JIT Costs speed in every engine for a difference in the last bit; the levels above are documented instead.
    One run per calibration evaluation The loss is noise, and Nelder-Mead stops anywhere.
    The mean as the default summary What to fit is a modelling choice; the mean of runs where half go extinct describes no run.

    Guards: crates/commol-random/ (tests, with the stored first values of each sampler in tests/reference_values.txt), py-commol/src/engine.rs (a_stochastic_engine_repeats_a_run_from_its_seed, an_aggregate_stochastic_engine_repeats_a_run_from_its_seed, a_deterministic_engine_ignores_the_seed), crates/commol-stochastic/tests/oracles.rs::a_run_depends_on_its_seed_and_not_on_where_it_reports, crates/commol-calibration/src/types.rs (replicate_tests), tests/model_kinds/test_stochastic.py.

    Whole units in a stochastic engine¶

    A stochastic engine moves whole units, so it starts from whole amounts. check_model (crates/commol-model/src/builder.rs, called by build and by every engine) rejects a total that is not whole, and initial amounts that are not whole unless the settings of the engine name a Rounding (crates/commol-core/src/types/engine.rs); the message lists both. There is no default:

    rounding Start of each run (Units::begin in crates/commol-stochastic/src/units.rs)
    "largest_remainder" The same whole amounts: each amount rounded down, the units left over to the largest remainders, the first compartment first on a tie
    "random" A multinomial draw of the total with the fractions of the model, from the generator of the run

    The engine rounds at the start of a run, not when it is built, so a value that calibration writes (InitialConditionPlan) goes through the same rounding, and "random" draws after the values are written. With no rounding, a written value that is not whole is an error.

    Alternative Why not
    Largest remainder by default With small amounts the rounding is a modelling choice: half a unit in each of ten groups starts five groups with one unit and five with none, which decides which groups can start a process at all. The library would choose it without notice.
    Random rounding by default The same objection, the other way.
    Reject every amount that is not whole Most stratified models would fail, with no way out but to compute whole amounts by hand.

    A per-step probability of StochasticSteps outside [0, 1], or proportional rates out of one compartment that sum to more than 1, are an error that names the compartment, the step and the flows (SimulationError::Infeasible), not a clamp: a binomial draw has no meaning outside [0, 1], and a clamp would change the model without notice.

    Guards: crates/commol-stochastic/tests/oracles.rs (amounts_that_are_not_whole_need_a_rounding, the_largest_remainder_starts_every_run_from_the_same_whole_amounts, a_random_rounding_starts_on_average_from_the_amounts_of_the_model, calibrated_initial_conditions_go_through_the_rounding, a_negative_rate_or_probabilities_above_one_fail_at_their_step), tests/stochastic/test_whole_units.py.

    The solver is diffsol¶

    The differential engine keeps no numerical method of its own: diffsol (pinned to a minor version, ~0.17.1) solves the system with tsit45 or bdf. bdf takes the Jacobian-vector product by finite differences (RightHandSide::jac_mul), one extra right-hand-side evaluation, because a symbolic derivative of every rate would be new numerical code. The matrix is dense (nalgebra) below SPARSE_THRESHOLD state components and sparse (faer) from there; diffsol finds the sparse pattern by passing NaN through J·v. Solver settings live in the model (Model.engine.settings), so a saved model reproduces a run.

    Guards: crates/commol-differential/src/tests.rs (bdf_solves_a_stiff_model_within_the_tolerance, a_large_stiff_model_uses_the_sparse_path).

    Calibration¶

    One meaning of an observation weight¶

    LossConfig::term and LossConfig::finish in crates/commol-calibration/src/types.rs compute every loss: sse is Σ w·r², rmse is √(Σ w·r² / Σ w), mae is Σ w·|r| / Σ w. The optimizer (calibration_problem.rs), the ensemble central loss (probabilistic/ensemble/mod.rs) and Python (central_fit_loss, through LossConfig.aggregate) all call them.

    Rule: never write a loss formula elsewhere. The central-fit gate compares the ensemble loss with the optimizer loss, so both must measure the same way.

    Guards: types.rs loss_tests; ensemble::tests::central_loss_uses_observation_weights_in_every_metric; tests/probabilistic/test_selection.py::test_central_fit_loss_uses_weights_in_every_metric.

    Nelder-Mead searches inside the bounds¶

    The objective clamps values to their bounds, so the loss is flat outside them, and a simplex that crosses a bound collapses there. Nelder-Mead therefore searches an unbounded u and scores x = lo + (hi − lo)·(sin u + 1)/2 (SineTransform and BoundedProblem in optimization.rs). Its evaluations and its result are recorded in x. converged is true only for SolverConverged and TargetCostReached (optimization::converged).

    Rule: report and record values in x, never in u. Every optimizer run, the verbose one included, goes through optimize_observed.

    Guards: optimization::tests; tests/calibration/test_optimizers.py.

    A Simulation follows its model¶

    Simulation keeps the JSON its engine was built from. run, engine and simulation_outputs compare it with model_dump_json() and rebuild the engine when it differs (Simulation._sync_engine), and run resets the engine first. Calibrator takes simulation.engine when it is created, so the check is in the property, not only in run.

    Guard: tests/simulation/test_runs.py.

    Results¶

    One confidence-interval convention¶

    ci_percentiles (api/probabilistic/intervals.py) is the only place that turns a confidence level into percentiles. member_statistics reduces each ensemble member to the quantity of interest first, and then takes percentiles across members. Taking percentiles first gives a band that describes no member.

    Rule: every new interval goes through these two functions.

    A description is data, rendered apart¶

    Model.describe(layout) returns a ModelDescription (context/description.py): sections with a key, a title and blocks from a closed set of Pydantic models (Text, Table, Equations, StateGraph, Matrix). The sections every kind shares come from Model (context/_model/describe.py); a kind adds its own through ModelStructure.describe (Aggregate: context/_model/aggregate_description.py). The renderers (api/description.py) read only blocks, so a new kind renders in every format with no new renderer. The form of the dynamics and the schedule come from the engine's list (EngineType::dynamics_form), because one structure runs as equations or as events depending on its engine.

    Part Rule
    Equations Computed by the code of the planner's flows (transition_flows), so a description shows what the engine simulates. The text rendering keeps the compact and expanded forms line by line.
    Diagrams Mermaid in the Markdown rendering, only for a graph that is not expanded; Graphviz DOT for every graph in a .dot file. Text, LaTeX and JSON draw none.
    Layouts "default": overview, entities, dynamics, schedule, initialization, parameters, outputs. "odd": the ODD protocol; an element commol cannot fill is marked TO_BE_WRITTEN. A section with no blocks is left out of every rendering.
    Alternative Why not
    A printer per kind and per format (the former print_equations) Every kind writes every format, and no caller can read or export the description.
    A free-form dict The renderers would guess its shape; typed blocks are checked by Pydantic and ty.
    An image (PNG, SVG) of a graph Needs Graphviz or a browser at run time, a dependency for a view.
    TikZ in the LaTeX rendering Needs node coordinates, so a layout algorithm; a PDF made from the DOT file does the same.

    Guards: tests/description/ (test_equations*.py check the lines of the equations through equation_forms; test_rendering.py checks the snapshots of description/snapshots/, parses the DOT with pydot and compiles the LaTeX with latexmk when they are installed), tests/building/test_engine.py (every engine gives a form).

    Reports¶

    api/reporting.py returns blocks of data, not documents: simulation_report (observed values, series, accumulators) and applied_parameters_report (calibrated parameters, and the sections of the model kind: initial_conditions for an aggregate model).

    • A single run and an ensemble differ only at the leaves (ReportLeaf).
    • The key order of each entry is part of the contract, because it changes saved JSON files.
    • Labels and summary figures belong to the caller, because they carry domain vocabulary.

    Guard: tests/reporting/.

    Model files are written in full¶

    Model.to_json writes every field, nulls included. Dropping nulls is not round-trip safe: an uncalibrated Parameter.value or BinFraction.fraction would lose a required key and fail to reload. render_json (context/_model/serialization.py) keeps files readable by writing long numeric arrays on one line. It is internal on purpose: an output format in the public API becomes a compatibility promise.

    Public models forbid unknown fields¶

    Every public Pydantic class sets model_config = ConfigDict(extra="forbid"). An unknown field, such as a misspelt or an old name (window_steps), raises a ValidationError that names it, instead of being dropped with no error.

    Guard: tests/building/test_unknown_fields.py.

    Security¶

    Every user expression is validated¶

    Rate expressions (context/dynamics.py) and calibration constraints (context/calibration.py) pass through validate_expression_security (utils/security.py) before they reach the engine. The limits are in SecurityConfig.

    Rule: any new field that accepts an expression must call it.
