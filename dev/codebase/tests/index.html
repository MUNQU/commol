    Tests¶

    Back to Codebase Guide

    Where a Python test goes, how it builds its model, what it must check, and how long it may take. The Python tests live in py-commol/tests/; the Rust tests are #[cfg(test)] modules and the tests/ folder of each crate.

    Layout: one package per guide page¶

    A test goes in the package of the guide page that documents the behavior it checks, so "where is the test of X" has the same answer as "where is the guide of X". A pure-Python helper (utils/security.py, context/axis_units.py, api/inference/intervals.py) goes in the package of its feature. The exceptions are reference_models/, which checks published models across features (see Reference models), and model_kinds/, which runs a model kind that is not aggregate through every generic layer.

    Package Tests of Guide page
    building/ The builder, parameters, stratifications, reserved names, save and load Building Models
    transitions/ Flows, $compartment, stratified rates, impulses Transitions
    rates/ Formulas, functions, variables, expression security Mathematical Expressions
    axis_patterns/ AxisPattern formulas, runs and schedules Axis Patterns
    initial_conditions/ Bin, stratification and compartment fractions; the initial state Building Models
    simulation/ Runs, run_at, results and their positions, differential models, outputs, the window grid and windowed totals, AxisUnits Running Simulations
    stochastic/ The stochastic engines of an aggregate model through the layers: their means against the deterministic engines, whole units, calibration with replicates (the closed forms are in crates/commol-stochastic/tests/oracles.rs) Stochastic Simulation
    units/ Unit checks of an equation (test_unit_checks.py), of the operators and the functions of the language (test_expression_units.py) and of a model (test_model_units.py); the step unit, the unit of the axis and a position in a rate (test_time_units.py); the dates of an axis with an origin (test_calendar_axis.py) Units
    description/ Model.describe, its sections and blocks, the renderers and their snapshots (description/snapshots/), the equations of the dynamics (equation_forms in support/description.py) Describing a Model
    calibration/ One file per calibration page: test_problem.py, test_optimizers.py, test_starts.py, test_constraints.py, test_observations.py, test_initial_conditions.py, test_write_back.py; and a run below zero, which the calibration avoids (test_infeasible_runs.py) Model Calibration and its sub-pages
    uncertainty/ The parameter sample, the one quantile, the predictive, the scores, the entry points Calibrator.uncertainty and SensitivityAnalysis.run, the range rule of every setting (test_ranges.py) and of every count and every seed a binding or an entry point takes (test_counts.py), and the coverage harness (test_coverage.py, marker coverage_study) Uncertainty
    parallelism/ The setting of the threads and its levels, the threads that each parallel method runs on, a swarm in parallel, and one result for one seed whatever the threads and the level (test_threads.py). A new parallel method adds a case to METHODS Threads and Parallelism
    reporting/ Reports Reports
    plotting/ The figures of results (plot of SimulationResults, SimulationReplicates, Predictive and of the results of sensitivity methods and profiles), their panels (panels.py) and their style: what every figure does (test_figures.py), the figures of a run (test_run_figures.py), the bands of a predictive and of replicates (test_band_figures.py), the panels of observed series (test_observed_series.py) and plot_compared (test_compared.py) Running Simulations
    docs/ The documentation examples and the API coverage (marker docs) —
    reference_models/ Published models against their stated results, one module per model family — (across features)
    model_kinds/ The test model kind (support/kinds.py) through a simulation, a calibration, a report and a plot; the check that an engine runs its kind; the variants of a structure (UnstratifiedVariant). It needs the extension built with --features test-kind. — (across features; Design decisions)
    suite/ The rules of this page that a program can check, for the Python tests (test_rules.py) and for the Rust tests (test_rust_rules.py), the rules of what the engine holds: the names and ranges of the settings, the windows and the stub of the extension (test_engine_rules.py), the layers: no crate of crates/ depends on PyO3 or on the bridge (test_architecture.py), the plugin that records how long each test takes (durations.py), the settings of commol that the rules read: their names and the range constraints of the pydantic models (settings.py), the checks of the package as a whole: its version (test_version.py) and its logging, in a fresh interpreter (test_logging.py), the checks of CI: its rights, its pinned tools, the workspace of the crates and the commands the documentation shows (test_workflows.py), and the checks of the scripts of .github/scripts/: the next issues and what can run in parallel (test_planning.py), the precedence levels (test_levels.py), the links of the releases (test_releases.py), the REST calls (test_github.py), the affected issues (test_affected.py), the release notes (test_release_notes.py) and the Rust lines no test runs (test_rust_uncovered.py). No test calls GitHub: each one patches the REST calls (support/planning.py) —
    support/ No tests: the code the tests share. support/plotted.py reads figures and imports matplotlib, so tests/support does not import it: a module of plotting/ imports it by name —

    A module of tests/ has at most 600 lines. When it grows past that, split it by topic inside its package. tests/suite/test_rules.py checks the limit, that each package has a row in this table, and that the row of suite/ names each of its modules.

    Models: use the factories¶

    • Build models with the factories of tests/support/models.py: abc_builder (A → B → C), abcd_builder (A → B → C → D) and a_to_b_builder, and the special models override_builder, shared_category_builder, conditional_pathway_builder and mixed_units_builder (A and B in item, C in mg/l). A factory returns a FactoryBuilder: a ModelBuilder of the process and the Aggregate that lays it out (builder.structure, which set_structure replaces). A keyword overrides one part of the default model, so a test names only what it changes. build builds for difference equations; build_ode builds for differential equations, with the tight solver settings TIGHT by default; build_stochastic builds for a stochastic engine (STOCHASTIC_ENGINES, and MEAN_FIELD, the deterministic engine of each); run builds and simulates.
    • Build a model by hand only when one test needs it and no factory keyword expresses it. A model that a second file needs goes to support/.
    • Test models use abstract names, as examples do: bins A, B, C, parameters k1, k2, categories g1, t1. Only tests/reference_models/ and the support code that only it uses (support/oracles.py, support/flows.py) keep the names of their published source.
    • Fixtures that more than one module uses:
    • tests/conftest.py: abc_model and abc_simulation, the default model of abc_builder and its simulation; close_figures, which runs for every test and closes the figures it drew, and imports no plotting library when it drew none.
    • tests/calibration/conftest.py: truth, abc_builder at the values to recover, and truth_run, 100 steps of it.
    • tests/uncertainty/conftest.py: calibrator, which fits k1 and k2 of abc_builder to truth_run_50, 50 steps at the values to recover; simulation, the default model of abc_builder, for the sensitivity methods.
    • tests/plotting/conftest.py: run, 100 steps of the default model of abc_builder; prcc_result, morris_result, sobol_result and profile_result, the results that the figures draw.

    A fixture name has one meaning in the whole suite: no two conftest files define a fixture of one name, and tests/suite/test_rules.py checks it. A fixture is function-scoped unless its cost is measured; a wider scope never holds an object a test can change. A class-scoped fixture is never an instance method (removed in pytest 10).

    Every test checks a result¶

    A test compares a result with an oracle:

    Oracle Example
    A value computed by hand in the test reference_run (tests/support/reference.py) evaluates the flows in plain Python, as the engine does: every flow from the state at the start of the step, no clamping. tests/rates/test_formulas.py compares whole trajectories with it.
    An analytic value An outflow rate d on every bin gives total(t) = total(0) (1 - d)^t (tests/transitions/test_compartment_placeholder.py).
    An invariant A total that the model keeps (assert_total_conserved); two paths that must agree, such as a bin id and the explicit sum of its compartments.
    What a stated result predicts about a run tests/support/oracles.py, for the reference models: final_size solves the final size relation, assert_threshold checks that a model grows at a reproduction number of 1.05 and decays at 0.95, settled reads a limit once doubling the horizon no longer moves it.

    "It runs" is not a result. A test whose only check is that no exception occurs is allowed only when the exception is its subject, such as a validator that accepts a valid input; it calls assert_accepted(check, *args) (tests/support/assertions.py), which fails with the message of the rejection.

    A test checks the behavior of commol. It does not check:

    • the behavior of Python, pydantic, NumPy or another library, such as a str path that pathlib accepts, or an unknown keyword that Python rejects;
    • a default of a pydantic model or of a binding;
    • an attribute read back as the test set it;
    • the absence of an API that was removed: that is history, not behavior.

    tests/suite/test_rules.py and tests/suite/test_rust_rules.py check the part of this that a program can read: every Python test has an assert, a pytest.raises, pytest.warns or pytest.fail, a call of np.testing.assert_*, or a call of a helper of tests/ that has one; every Rust test has an assert*!, panic! or unreachable!, calls a function of its crate that has one, is #[should_panic], or returns a Result. Review checks the rest.

    Duplicates¶

    Two tests do not check the same behavior with the same inputs. Candidates come from the coverage of each test:

    COVERAGE_CORE=ctrace pytest --cov=commol --cov-context=test --cov-report=

    The sysmon core, the default of coverage on Python 3.14, records a line only for the first test that runs it, so it gives most tests no context. Two tests of one module whose covered lines are equal, or one inside the other, are a candidate. Coverage does not decide: two tests can run the same lines and check different results. Read both, and keep one only when the other checks nothing that it does not: the same output for the same input, or a weaker check of the same output ("+" in formula against the exact formula).

    Tolerances¶

    • assert_close(actual, expected, rel=…, abs=…) (tests/support/assertions.py) needs a stated tolerance, and reports the key and the index of the first difference.
    • ENGINE_REL = 1e-9 compares the engine with a hand computation of the same arithmetic: only the order of the floating-point operations differs.
    • ODE_REL = 1e-6 compares a differential model with a closed form, a final size or an equilibrium. flow_model solves with FINE (TIGHT with atol = 1e-12), so the error of a value near zero stays below its own size.
    • pytest.approx with its default (relative 1e-6) suits a single value computed by hand.
    • An optimizer result states the tolerance its convergence allows, for example abs=1e-5 for Nelder-Mead on noise-free data.
    • np.testing.assert_allclose skips masked values. Read the points of a matplotlib collection as floats (np.asarray(offsets, dtype=float), as scatter in tests/support/plotted.py does), so a point at None is NaN and fails.

    Reference models¶

    tests/reference_models/ shows that commol can state published models and computes their stated results. A module holds one model family and is named after the published model (test_pulse_vaccination.py); a test checks one stated result (test_the_fixed_point_starts_the_periodic_orbit).

    • Attribution. The module docstring has a References section in the NumPy format with the original papers of the model and of its parameter values (authors, year, title, journal, DOI). A value or a result taken from a paper cites it in a comment next to the value. A model with no primary source is not added.
    • Independent oracle. The expected value comes from the stated result, computed with math or numpy: a closed form, a root of the final size relation, a spectral radius. A test never compares commol with commol. A quantity that commol does not output, such as a reproduction number, is checked through what it predicts about a run (tests/support/oracles.py).
    • Equations. To check that a model has the stated equations, increments reads its right-hand side at one state: a difference-equation step adds the flows of the state it starts from, and both engines compile the same flows.
    • Tolerances. ENGINE_REL for a discrete model, ODE_REL for a differential one; an asymptotic result is read with settled, and the test states its horizon.
    • Gaps. A model that commol cannot state, or computes wrong, gets a test marked as Skips, expected failures and ignored tests says, with the open issue of the finding.

    To add a test, write the model with Flow and flow_model (tests/support/flows.py) from the initial value of each bin, compute the stated result in the test, and cite the papers.

    Skips, expected failures and ignored tests¶

    • An xfail is strict=True and its reason starts with the open issue that fixes it (reason="#196: …"): the fix makes the test pass, and the strict marker then fails the run until the fix removes it.
    • A test that skips when an optional dependency is missing runs in at least one CI job: the dev extra installs pydot, and Python Coverage and the job Test of Build on Ubuntu install latexmk.
    • A Rust #[ignore] gives a reason with the cargo test command that runs it, such as the benchmarks of crates/commol-differential/src/tests.rs. A benchmark also asserts that the methods it times give the same result.

    tests/suite/test_rules.py checks the xfail markers, and tests/suite/test_rust_rules.py the reasons of #[ignore].

    Time budget¶

    A test takes at most 1 s, setup and teardown included, in the job Test of Build on Ubuntu, which runs every test without coverage. Coverage slows a test that runs much Python up to ten times, so the run under coverage (Python Coverage) skips the check, and so does a run off Linux. A test over 0.5 s stays only if it checks what no faster test checks, with the smallest inputs that still check it: a shorter horizon, fewer steps, fewer replicates. tests/suite/durations.py records the time of each test, and test_slow_tests_are_listed runs last and fails on a test over the budget that the table below does not list.

    The coverage studies (coverage_study) are the one exception. A study counts how often an interval covers the truth over hundreds of synthetic data sets; fewer data sets widen its tolerance until it checks nothing, so it cannot shrink to the budget. They do not run less often than the code they check: Build runs them for every pull request that changes what they run, and the release runs them before it publishes (CI pipelines). test_every_coverage_study_runs_in_a_group_of_the_workflow checks that coverage.yaml runs each of them, and test_the_studies_run_for_a_change_of_any_crate_they_use that a change of commol-inference, of a crate it depends on or of the engines of their models (difference and stochastic) runs them.

    The check reads the wall time of the run, so a machine that runs other work at the same time can exceed the budget. pytest --durations=20 shows the slowest tests; Python Coverage prints them, slowed by coverage. A row names a test, or one case of a parametrized test with its parameter in brackets.

    Test Why it takes longer
    tests/description/test_rendering.py::TestLatex::test_the_latex_document_compiles It compiles the LaTeX description with latexmk; the first TeX run of the job loads its formats. No other test checks that the document compiles.
    tests/plotting/test_panels.py::test_the_panels_of_a_run_need_no_matplotlib It starts a new Python process that imports commol and computes the panels of a run; only a new process shows that the panels import no matplotlib, because the other tests of the session import it first.
    tests/docs/test_examples.py::test_page_examples_run[docs/guide/simulations.md] It runs every example of the page, which draws and saves four figures with matplotlib, one label per plotted position; the figures are what the page documents.
    tests/docs/test_examples.py::test_page_examples_run[docs/guide/examples.md] It runs the ten examples of the page, from a first run to a fit with a bootstrap, its predictive and two scenarios, and draws and saves their figures with matplotlib; the page shows the whole workflow, and its replicates and bootstrap are already small.
