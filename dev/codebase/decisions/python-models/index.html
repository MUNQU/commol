    Python Models¶

    Back to Design decisions

    How the Pydantic models of the Python package read their fields, check their values and compare, and which names of the package are public.

    Public models forbid unknown fields¶

    Every public Pydantic class sets model_config = ConfigDict(extra="forbid"). An unknown field, such as a misspelt or an old name (window_steps), raises a ValidationError that names it, instead of being dropped with no error.

    Guard: tests/building/test_unknown_fields.py.

    The public surface holds only what a user writes¶

    The public modules hold the names a user writes: the builder and its conditions (StratificationCondition, StratifiedRate), the structures, the entry points, the settings and the methods. The data of the surface is py-commol/tests/suite/public_surface.py: EXPORTS, the names of each public module, and RESULTS, the results that public objects return.

    Kind of name Rule
    A result Not exported. The member that gives it has it as its return type, and its path entry is on the page of docs/api/ of that object.
    A choice among names A Literal in the signature, such as loss_function: Literal["sse", "rmse", "mae"]; no enum and no public alias of strings.
    A union of classes, a base, a part that the builder makes Private: a union is a type _Name = … alias, and a base is not exported.
    A pydantic validator or serializer A name that starts with _.
    An idea One public path: SimulationResults.sample and SimulationResults.windowed_totals read a run by id; the functions on one series are private.
    Alternative Why not
    Export each class a signature names About half the names are results, enums and unions a user never writes.
    An enum for each choice A name to import and learn for each choice; a string is checked by pydantic with the same list of values.
    A dict for a condition No type check of its keys, and a second shape of one idea next to the class.

    Guards: tests/suite/test_architecture.py::test_the_public_surface_is_the_table, tests/suite/test_architecture.py::test_a_choice_is_a_literal, tests/suite/test_architecture.py::test_no_public_member_is_internal, tests/docs/test_reference.py::test_each_result_is_on_the_page_of_its_object and tests/building/test_conditions.py::test_a_condition_is_one_class.

    One module per page of the guide¶

    The root commol holds the main flow: build, the structures, simulate and calibrate. Every other public name is in the module of its page of the guide (commol.engines, commol.plotting, commol.parallelism, commol.distributions, commol.quantities, commol.observations, commol.uncertainty, commol.scores, commol.resampling, commol.profiles, commol.local, commol.smc, commol.conformal, commol.identifiability, commol.sensitivity), and the root exports no name of a module. Each public module is a package that holds its code; the code of the root is in private packages (_model, _simulation, _calibration, _problem, _fit, _data, _statistics, _build). Each public module logs as logging.getLogger("commol.<module>"), and the code of the root as commol, so no record names a private path.

    Alternative Why not
    Every name in the root About a hundred flat names; a user meets the names of every page at once.
    One module per layer of the code (api, context) The layers follow the code, not what a user reads, and their areas import each other.
    One commol.uncertainty for every family of methods A module of about thirty-five names.
    logging.getLogger(__name__) The name of a record would be a private path, which changes with the code.

    Guards: tests/suite/test_architecture.py::test_each_public_name_has_one_home, tests/suite/test_architecture.py::test_the_packages_are_the_modules, tests/docs/test_reference.py::test_each_module_has_its_page and tests/suite/test_logging.py::test_a_record_names_the_public_module.

    The layers of the package¶

    The packages form one order, and each imports only the packages below it: at the top of a module, in a function and under TYPE_CHECKING alike. From the bottom:

    Layers What they hold
    commol_rs, _build, _data, _statistics The extension, the build, the base of every data object with the port of the bridge, the weighted statistics
    parallelism, engines, distributions, quantities, _fit, observations, _problem Settings and values that read no model
    _model The model and its structure
    plotting The one drawing layer: data types of panels and charts, and the drawing
    _simulation Runs and replicates, their reports and the data of their figures
    uncertainty A sample, its predictive and the data of its figures
    _calibration The calibrator and the bases of the methods (InferenceMethod, CalibrationPort, run_method)
    scores, resampling, profiles, local, smc, conformal, identifiability, sensitivity The method families, each with its methods, results and runners
    commol The root, which imports what the main flow writes

    A package that needs something of a package above it reads it through a protocol of its own: _model reads a sample through SummarizedSample (_model/report_entry.py), a report and a figure read prediction intervals through PredictionIntervalsData (_data/intervals.py), plot_compared reads a result through PanelSource (plotting/panels.py), and a runner reads a calibrator through CalibrationPort (_calibration/method.py). Code that serves one object lives with it: the block of IdentifiabilityReport.report in identifiability/report.py, the delta band of a local approximation in LocalResult.delta_band. Each method names its runner in the class variable _runner, so the calibrator imports no method.

    Alternative Why not
    An order with listed exceptions Each exception is a cycle that the next change makes longer; the test would guard less with each one.
    Imports upward in a function or under TYPE_CHECKING only They hide the cycle from Python, not from the reader or the type checker: the lower package still depends on the upper one.
    A registry that each family of methods fills when it is imported The result of an entry point depends on which modules were imported before; a method that names its runner works in any order of imports.

    Guards: tests/suite/test_architecture.py::test_the_dependencies_point_one_way and tests/suite/test_architecture.py::test_the_check_names_an_import_upward.

    A value of a model has its rule in the engine¶

    An initial amount, the fractions of a stratification, an impulse and the points of a series have their rule once, in crates/commol-model/src/rules.rs (check_bin_amount, check_compartment_amount, check_fractions, check_impulse, check_series). The model compiler calls them when it compiles a model, set_initial_condition when a calibration writes an amount, and the Python object of the value when it is built: the validators of InitialConditions, Transition and SeriesValue call the bindings of commol_rs.model. A value outside its rule fails at the line that sets it, with the message of the engine. A range is a Real of commol-core after the owner of the value (Bin 'B': initial amount is a finite number of at least 0, got -1); a rule that is not a range, such as one point per position or fractions that sum to 1, has one message in the same module. update_stratification_fractions gives the one category left unnamed the rest of 1, in every split of a stratification split by category, and checks the result with check_fractions; the rule that at most one category is left unnamed stays in Python, because it is a rule of the update, not of a value, and the engine never gets an update.

    Alternative Why not
    A check in Python and one in the compiler Two messages for one rule, and rules that only one side has, such as the series without a point.
    A check only when the model compiles The error comes far from the line that set the value.
    A row of RANGES for the object (RangeChecked) A rule of RANGES has a fixed name, so the message cannot name the bin or the transition, and (period, offset) has two rules.

    Rule: a new value of a model gets its rule in rules.rs, which the compiler and the validator of its Python object call.

    Guards: tests/building/test_value_rules.py, crates/commol-model/tests/value_rules.rs.

    A data object crosses as the JSON of its dump¶

    Every data object of the Python API that reaches the engine, the model, the calibration problem and each inference method included, crosses as the JSON of its model_dump() (engine_json of py-commol/commol/_data/engine_json.py). The bridge reads it with one helper, read of py-commol/src/json.rs, into the type the engine owns, which takes the spelling of the Python API (rename_all = "snake_case") and denies unknown fields. An error names the path of the field and gives the message of the engine (optimization_config.inertia_factor: inertia_factor is a number greater than 0, got -1).

    A number that is not finite crosses as standard JSON text, "Infinity", "-Infinity" or "NaN", in both directions. Python writes it with the serializer of pydantic in the mode inf_nan_mode="strings", the mode that the setting ser_json_inf_nan="strings" of a model selects, once for every class in engine_json. The reader is serde_json, and its Value reads such a text as a number only where the type asks for a number (deserialize_f64), so a label "NaN" stays text; a range rule reads the text as its number, so an infinite setting gets the message of its rule. The writer of the engine, commol_core::json::write, and the tree of a formula write the same three texts, and so does the JSON of every result: ResultModel sets ser_json_inf_nan="strings" for all of them. A value of an enum of the engine crosses as the JSON of its name (engine_json(name)), read with serde: what a rate keeps (RateKeeps), an engine (EngineType), a model kind (ModelKind), the levels of the threads (Levels), and the score and the pooling of a conformal method (ScoreAndPooling). No binding reads a name with a from_name of its own (tests/suite/test_architecture.py).

    Each union of classes carries one tag, kind, with a default, so a field is never read by the first variant that matches; tagged! of commol_core::json reads the tag, keeps the path and checks the range rules of the variant. A method crosses whole, into one settings type of crates/commol-inference/src/settings/, and the engine decides what the method needs: the fit with its starts, the calibration of η, the threshold of a profile and the checks of the names. A field that holds a result with behavior in the engine, such as a sample, crosses as its handle: the class names it in _engine_handles, and engine_handles gives it as a keyword argument. A #[pyclass] is a handle or a result, never data.

    Alternative Why not
    A PyO3 class for each data class, filled field by field in Python Three shapes of each value (the pydantic class, the conversion, the PyO3 class), four edits per field, and nothing checks that they agree.
    The fields of a method as positional arguments A long signature per method, and a copy of its fields in the runner.
    An untagged union No path in the error, and the first variant that matches wins.
    pythonize (Python objects to serde with no string) A second mechanism next to the JSON of the model.
    The crate json5, which reads Infinity and NaN as numbers A grammar far wider than three values (comments, trailing commas, unquoted keys, hexadecimal numbers) at a port that must be small, and a second convention next to the tree of a formula.
    The constants Infinity and NaN without quotes They are not JSON: a standard reader rejects them.

    Rule: a new field of a data object gets the same name in its Rust type, and nothing else; a new data class gets its Rust type, an entry of objects! in py-commol/src/json.rs and a valid object in tests/support/data_objects.py.

    Guards: tests/suite/test_bridge.py (the engine reads back each dump), tests/suite/test_architecture.py (no data class in the bridge, no conversion in Python, each runner sends its method whole), tests/calibration/test_settings.py (the path of an error), tests/uncertainty/test_ranges.py (an infinite setting gets the message of its rule), tests/uncertainty/test_results_equality.py (the JSON of a result), crates/commol-core/tests/json.rs, crates/commol-calibration/tests/test_json.rs.

    Results compare by their values¶

    Every result of commol compares with one rule, ComparedByValue (py-commol/commol/_data/result_model.py). Its subclass ResultModel is the base of every result model: the result of a calibration (CalibrationResult, CalibrationHistory), of each uncertainty, identifiability and sensitivity method, the parameter sample, the bands of a predictive, the summary of a scenario, a score, and their parts (StartSummary, SeriesIntervals, …); it compares its public fields. The results of a run and of replicates (SimulationResults, a dict, and SimulationReplicates, a list, in py-commol/commol/_simulation/results.py) compare their values or runs, positions, seed and model. Two results are equal when they are of one class and those values are the same. The comparison reads canonical, the values as nested tuples, also of a setting or a Model inside a result, such as the Threshold of a ProfileResult:

    Value Rule
    NaN Equal to every NaN, whatever the object
    0.0 and -0.0 Equal, with one hash, as == of floats
    A list or a tuple Item by item, in order; a list is not equal to a tuple
    A dict Its items, in any key order
    A private attribute, such as the Rust sample of ParameterSample Not compared

    An object that is not a result, such as a plain dict or list with the same items, is not equal to one: __eq__ gives False, not NotImplemented, so dict.__eq__ does not answer by the values, and __ne__ is its negation. A frozen result (frozen=True) has the hash of canonical, so equal results have equal hashes. A result that can change (SimulationResults, SimulationReplicates, CalibrationResult, CalibrationHistory) has no hash. A setting keeps the == of Pydantic.

    Alternative Why not
    The == of Pydantic A list compares the identity of its items first, and a NaN is not equal to itself, so two runs with one seed differ when they hold a NaN: the engine gives new objects. It also compares the private attributes.
    No == on results A caller could not check that a seed repeats a result.
    Comparing model_dump_json() Each caller must know it, and a string is built for each comparison.
    An __eq__ per result Rules that drift apart from one result to the next.
    The == of dict and list for runs and replicates, with NaN equal to NaN Two rules, and runs at other positions or with other seeds and the same values stay equal.

    Rule: a new result model has ResultModel among its bases, and a new method returns one.

    Guards: tests/uncertainty/test_results_equality.py, tests/uncertainty/test_results_equality.py::test_every_method_of_commol_returns_a_result_model and tests/simulation/test_results_compare.py.
